---
title: "Add filtering to a list endpoint"
description: "Declare which operators a field accepts, let the framework validate and resolve them, and read typed values in your controller."
---

Filtering in Apivalk is route-level: you tell the route which fields are filterable and which operators each one accepts, the framework validates and resolves what the client sends, and your controller reads typed values from `$request->filtering()`.

## 1. Declare filters on the route

```php
use apivalk\apivalk\Documentation\Property\DateProperty;
use apivalk\apivalk\Documentation\Property\EnumProperty;
use apivalk\apivalk\Documentation\Property\IntegerProperty;
use apivalk\apivalk\Documentation\Property\StringProperty;
use apivalk\apivalk\Router\Route\Filter\DateFilter;
use apivalk\apivalk\Router\Route\Filter\EnumFilter;
use apivalk\apivalk\Router\Route\Filter\IntegerFilter;
use apivalk\apivalk\Router\Route\Filter\Operator;
use apivalk\apivalk\Router\Route\Filter\StringFilter;
use apivalk\apivalk\Router\Route\Route;

public static function getRoute(): Route
{
    return Route::get('/api/v1/animals')
        ->filtering([
            new EnumFilter(new EnumProperty('status', 'Lifecycle status', ['active', 'archived']), Operator::EQ, Operator::IN),
            new StringFilter(new StringProperty('name', 'Name'), Operator::CONTAINS),
            new IntegerFilter(new IntegerProperty('age', 'Age in years'), Operator::GTE, Operator::LTE),
            new DateFilter(new DateProperty('born_at', 'Date of birth'), Operator::GT, Operator::LT, Operator::NULL),
        ]);
}
```

One filter per field, however many operators that field should accept. The first operator is also the one flat notation resolves to, so `?status=active` means `status[eq]=active` above.

A filter class only accepts operators that make sense for its type. `new StringFilter($property, Operator::GTE)` throws when the route is built, listing what is supported:

| Filter class | Operators |
|---|---|
| `IntegerFilter`, `FloatFilter`, `DateFilter`, `DateTimeFilter` | `EQ`, `NEQ`, `IN`, `GT`, `GTE`, `LT`, `LTE`, `NULL` |
| `StringFilter` | `EQ`, `NEQ`, `IN`, `LIKE`, `CONTAINS`, `NULL` |
| `EnumFilter`, `ByteFilter`, `BinaryFilter` | `EQ`, `NEQ`, `IN`, `NULL` |
| `BooleanFilter` | `EQ`, `NULL` |

## 2. Clients pick the operator

```
GET /api/v1/animals?age[gte]=3&age[lte]=10
GET /api/v1/animals?status[in]=active,archived
GET /api/v1/animals?born_at[null]=true
GET /api/v1/animals?status=active
```

The last one is flat notation, a shortcut for the first declared operator. `IN` takes a comma-separated list. `NULL` takes a boolean: `true` matches null values, `false` matches non-null ones.

`RequestValidationMiddleware` rejects with `422` when the client sends an operator the field does not declare, a value of the wrong type, or a combination that can never match such as `age[gte]=10&age[lte]=3`. A parameter you never declared as a filter is ignored.

## 3. Read values in the controller

Every operator you declared is a typed property on the filter. Name your own request class in `__invoke()`, otherwise the generated shapes cannot resolve (see [Typing `$request`](/http/controller)):

```php
public function __invoke(ListAnimalsRequest $request): AbstractApivalkResponse
{
    $filters = $request->filtering();

    $qb = $this->animals->query();

    if ($filters->status->has(Operator::EQ)) {
        $qb->where('status', '=', $filters->status->equal);         // string
    }

    foreach ($filters->status->in as $status) {                     // string[]
        $qb->orWhere('status', '=', $status);
    }

    if ($filters->age->greaterThanOrEqual !== null) {
        $qb->where('age', '>=', $filters->age->greaterThanOrEqual); // int
    }

    if ($filters->born_at->isNull === true) {
        $qb->whereNull('born_at');
    }

    // ...
}
```

| Operator | Property |
|---|---|
| `Operator::EQ` | `equal` |
| `Operator::NEQ` | `notEqual` |
| `Operator::IN` | `in` |
| `Operator::GT` | `greaterThan` |
| `Operator::GTE` | `greaterThanOrEqual` |
| `Operator::LT` | `lessThan` |
| `Operator::LTE` | `lessThanOrEqual` |
| `Operator::LIKE` | `like` |
| `Operator::CONTAINS` | `contains` |
| `Operator::NULL` | `isNull` |

`has(Operator::EQ)` answers whether the client supplied that operator, which is what you want for boolean and integer filters where `false` and `0` are legitimate values. `raw(Operator::EQ)` returns the literal string the client sent, useful for audit logs.

Reading an operator the field does not declare throws a `LogicException`. That is a mistake in your code, not client input, so it fails loudly on the first run.

## 4. Iterate when you want to apply them generically

```php
foreach ($filters as $field => $filter) {
    foreach ($filter->conditions() as $operator => $value) {
        // $operator is 'eq' | 'gte' | 'in' | …, $value is already typed
        $qb->where($field, $this->toSqlOperator($operator), $value);
    }
}
```

## Inside a resource

Resources expose `availableFilters()`, and `AbstractListResourceController` wires them into the route:

```php
public function availableFilters(): array
{
    return [
        new EnumFilter(new EnumProperty('status', 'Status', ['active', 'archived']), Operator::EQ),
        new StringFilter(new StringProperty('name', 'Name'), Operator::CONTAINS),
    ];
}
```

See [the resource CRUD how-to](/how-to/resource-crud).

## Filters as a request body

Add `->enableQuery()` to the route to also accept it as an [RFC 10008](https://datatracker.ietf.org/doc/rfc10008/) `QUERY` request, where the filters arrive as JSON:

```
QUERY /api/v1/animals

{"age": {"gte": 3, "lte": 10}, "status": {"in": ["active", "archived"]}}
```

Same declaration, same `FilterBag`, same validation. Sending both a body and query-string filters on one request is a `422`.

It is opt-in because a gateway that does not know the method drops the request before it reaches you, and because generated SDKs would otherwise expose two calls for the same read.
